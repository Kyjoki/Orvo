# Демонстрация первой версии

Этот сценарий выполняется после локального запуска из README. Для показа без расходов используйте тестового поставщика с `ORVO_TEST_MODE=1`. Он проверяет движение данных и управление исполнением, но создаёт заранее определённый текст вместо содержательного ответа облачной модели.

1. Войдите владельцем, задайте имя и часовой пояс. В настройках сохраните `test/deterministic` и проверьте подключение. Интерфейс должен явно указать тестовый провайдер. Для реального Gateway сначала настройте серверный ключ и доступную модель; проверка может расходовать токены.
2. Откройте «Агенты» и создайте сотрудника с нужным названием, ролью и инструкциями. После создания нового владельца список сотрудников пуст; при обновлении существующего пространства ранее созданные профили сохраняются. Создание профиля не запускает генерацию.
3. Откройте персональную панель одного агента. Проверьте Обзор, Чат, Память, Инструкции, Инструменты и доступ, Активность. Сохраните обычное сообщение: оно остаётся в истории, самостоятельный модельный ответ не запускается.
4. Добавьте агенту правило «В результатах перечислять допущения», явно выбрав область агента. Отредактируйте инструкции: версия увеличивается. Это память и инструкции приложения, без дообучения модели.
5. Создайте задачу «Подготовить план API интеграции Orvo с Ritm» с описанием и ожидаемым результатом. Передайте короткий Markdown как материал, без секретов. Выберите созданного сотрудника либо командный режим с двумя или тремя своими сотрудниками. Запуск ограничен тремя последовательными этапами; он не запускает всю команду разработки.
6. Откройте карточку задачи, перезагрузите вкладку и наблюдайте этапы из серверного состояния. Тестовый результат должен сохранять явную пометку. Для серверной паузы/отмены используйте отдельную задачу: быстрый тестовый ответ может завершиться раньше нажатия; нельзя выдавать это за проверенную остановку долгого платного вызова.
7. Для демонстрации подтверждения заполните предложение общей памяти, например «Ritm подключается только через отдельный разрешённый API-модуль». Дождитесь запроса: проверьте агент, параметры, область, последствия и срок. До решения общего правила быть не должно. Подтвердите один раз; правило появляется в памяти пространства, задача продолжает обработку. Отказ не публикует запись.
8. Раскройте реально сохранённый результат, скопируйте и скачайте Markdown. Примите результат либо запросите правки с комментарием. Предыдущая версия остаётся доступной; максимум три цикла правок.
9. Проверьте inbox и историю: уведомления сохраняются сервером. Отметьте прочитанным и обновите страницу. В настройках видны токены; при отсутствии данных о цене показывается недоступная стоимость, без фиктивного `$0`.
10. Переключите тему и «Офис / Список», зоны офиса. На телефоне используйте список по умолчанию, нижнюю навигацию и панель агента. Внешние GitHub, браузер, почта, shell и Ritm должны оставаться недоступными.

Код, подготовленный агентом, является предложенным материалом. В Orvo нет инструмента, который действительно меняет репозиторий, исполняет этот код, отправляет почту или публикует сайт. Живую модель, S3, уведомления на устройство и облачное восстановление этот локальный сценарий не подтверждает.

В предыдущей версии фактически проверены открытие 12 панелей и чатов тестовых профилей, мобильный список по умолчанию, сохранение чата/памяти/инструкций после обновления, сохранение сессии после рестарта, создание задачи → просмотр артефакта → принятие до `completed`. В прежней локальной production-сборке HTTP-проверки прошли для генерации, трёх ролей, 429-повтора, одноразового подтверждения, уточнения, паузы/продолжения и отмены до генерации. Это исторические проверки, а не требование о двенадцати сотрудниках или подтверждение нового сценария их создания. В Windows dev наблюдался `EPERM` runtime-файла; успешные production-проверки не означают, что этот dev-сбой устранён.
