# Поэтапное включение наблюдения за чатами

Сейчас рабочие сообщения не передаются из установленного на рабочем столе
расширения. Серверная обработка требует отдельного флага и выключена по
умолчанию. Никаких отправок в рабочие чаты не предусмотрено.

## Перед подключением

1. Проверить, что доступная через API модель совпадает с моделью в серверном
   расчёте расходов. Не использовать модель по умолчанию рабочего пространства
   вместо модели наблюдения.
2. Для строгого контроля расходов использовать отдельный проект OpenAI для
   наблюдения и настроить **hard spend limit $5 в месяц**. Обычное уведомление
   о расходах не останавливает запросы. Лимит отдельного проекта не должен
   прерывать остальные функции Orvo. Внутренний предел Orvo — 3000 анализов и
   расчётные $5 за календарный месяц в Asia/Qyzylorda. Ключ этого проекта
   сохраняется только на сервере как `ORVO_WATCH_OPENAI_API_KEY`; основной
   `OPENAI_API_KEY` остаётся для остальных задач Orvo.
3. Привязать расширение к Orvo отзывным ключом. Ключ не передавать в чат и не
   помещать в репозиторий. Проверить, что токен Telegram и ключ модели остаются
   на сервере, а расширение хранит только свой ключ в памяти браузера.

## Проверки до рабочих данных

1. Прогнать автоматические тесты Orvo и расширения.
2. Проверить на вымышленных сообщениях: вызов специалиста → срочно;
   конкретная просьба в закреплённом чате → внимание; выполненный возврат,
   новый заказ, выдача роли и приглашение в группу → без уведомления.
3. Повторить одно событие и проверить один анализ. При неопределённом ответе Telegram возможна повторная доставка уведомления, поэтому проверить отображение и обработку состояния очереди, включая сбой и восстановление.
   Превышение месячного количества и денежного резерва должно останавливать
   новые анализы. Ошибка модели или Telegram не должна раскрывать текст в логах.
4. Проверить выключение каждого переключателя, отзыв ключа, перезапуск
   браузера, две открытые вкладки и отсутствие передачи старых сообщений после повторного включения. Уже принятый сервером анализ может завершиться; уведомление после выключения должно блокироваться серверной проверкой флага.
5. Убедиться, что расширение не вызывает API отправки сообщений рабочего сайта,
   не заполняет поле ввода и не нажимает кнопку отправки.
6. Проверить доступность `gpt-6-luna` для отдельного ключа на одном вымышленном событии. Статус настроек проверяет наличие ключа и лимита, но сам по себе не подтверждает ответ модели.
7. Сверить число платных анализов с суммой доставленных, ожидающих и не доставленных уведомлений, учитывая решения «игнорировать». Отдельно проверить сбой после ответа модели до постановки уведомления в очередь: повтор не должен создавать бесконтрольный расход, но такое событие пока может быть пропущено.

## Ограниченный рабочий запуск

Включать только после предыдущих проверок. Сначала наблюдать за одной
рабочей сменой и сравнивать короткие уведомления с фактической важностью.
Расширение видит лишь доступные на странице превью, поэтому пропущенные
сообщения и неверная классификация всё ещё возможны. При избытке ложных
уведомлений выключить удалённую передачу и уточнить правила на обезличенных
примерах.
