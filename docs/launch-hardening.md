# 2FA, резервные копии и фоновая очередь

Проверено 19 октября 2026. Orvo остаётся личным офисом одного владельца с закрытой регистрацией. Preview и публичный Production — разные окружения.

## Постоянный адрес Preview

Выбранный владельцем адрес — `https://orvo-office.vercel.app`. Переменная `ORVO_PREVIEW_ORIGIN` задана только в Vercel Preview и определяет единственный доверенный HTTPS origin для Better Auth и CSRF. Если её нет, Preview использует собственный immutable URL; production `BETTER_AUTH_URL` на Preview по-прежнему не переносится автоматически. В Production эта переменная игнорируется.

UI страницы с длинного адреса новой сборки перенаправляются на alias с сохранением пути и параметров. API, `/ops`, `/eve` и Queue callbacks не перенаправляются. Внутренние RPC и секретные заголовки остаются привязаны к immutable origin. Host и forwarding headers не задают доверенные origins.

После нового релиза проверьте READY, затем назначьте alias новой проверенной сборке через `vercel alias set <deployment-url> orvo-office.vercel.app --scope <team>`. Обновите GitHub Environment `ORVO_DEPLOYMENT_URL` на её immutable origin и проверьте reconciler. Наличие manual alias не означает его автоматическое обновление при каждом CLI deploy. Для независимых Preview с другим адресом требуется отдельная настройка `ORVO_PREVIEW_ORIGIN` в целевой ветке.

Переход на новый hostname требует повторного входа из-за host-only cookies. Существующие пароль, Google Authenticator и данные владельца сохраняются. Vercel Authentication также действует на alias; переход к публичному Production не выполнялся.

## Двухфакторный вход

- В облаке второй фактор обязателен по умолчанию; явно задаётся `ORVO_REQUIRE_MFA=1`.
- `/security` доступна после пароля даже до подключения 2FA. Рабочие страницы и API закрыты до подтверждения второго фактора.
- Владелец вводит пароль, сканирует локально сформированный QR в Google Authenticator (или другом совместимом TOTP приложении) и подтверждает TOTP. Реальные секреты и коды не передаются в чат.
- Подтверждение закрепляется за конкретной серверной сессией. Сессии, созданные до подключения, требуют отдельного подтверждения.
- TOTP нельзя повторно использовать в течение 90 секунд. Доверие устройству отключено.
- Перебор ограничивается по IP и пользователю; смена IP не сбрасывает лимит активной сессии. Better Auth блокирует неудачные попытки во время входа.
- По прямому запросу владельца резервные коды отключены: нет выдачи, обновления или входа по ним; прежние коды отзываются миграцией. Вход использует пароль и TOTP. Потеря аутентификатора требует административного сброса, самостоятельного recovery flow нет.
- Отключение 2FA требует пароля и свежего TOTP. При обязательной 2FA отключение возвращает владельца к подключению защиты.

Для восстановления зашифрованного TOTP нужен совместимый `BETTER_AUTH_SECRET`. Сохраните его отдельно от резервного архива в защищённом месте. Смена этого секрета требует отдельного плана миграции MFA.

## Очередь без вкладки

После фиксации команды сервер публикует пробуждение `orvo-runtime` в Vercel Queues. Закрытый платформой consumer `/api/queues/runtime` доставляет сохранённые задания и управляющие команды в Eve. Уже принятые выполнения и ожидания срока живут в durable runtime. Опрос `/api/state` в Vercel не запускает очередь.

SQL leases, проверка владельца lease перед отправкой и сохранённый runtime ID защищают от обычной повторной доставки. Сбой одного элемента не останавливает остальные; порядок повторов учитывает прошлую попытку. При неопределённом исходе первоначальной отправки новое выполнение запрещено до ручной сверки, если сохранённый прогресс не доказывает начало работы. Это сознательная остановка, а не обещание exactly-once внешнего запроса.

Промежуток между фиксацией БД и публикацией сообщения восстанавливает отдельный процесс GitHub Actions. Он вызывает `POST /ops/reconcile` с отдельным `x-orvo-reconcile-secret`; этот ключ не даёт общего доступа к runtime RPC. Для защищённого Preview также используется штатный Vercel automation credential, который не заменяет авторизацию Orvo.

Очереди разделены по deployment. После нового релиза обновляйте `ORVO_DEPLOYMENT_URL` в GitHub Environment на проверенный immutable URL и проверяйте отложенные задачи прошлого deployment. Не удаляйте deployment с активными выполнениями.

## Ежедневные резервные копии

Workflow `.github/workflows/backups.yml` запускается в 22:23 UTC (03:23 Asia/Qyzylorda), допускает ручной запуск и хранит архивы 14 дней. Удаление старых архивов выполняется после новой успешной загрузки и ограничено собственным префиксом `orvo-backups/`.

Архив включает согласованный снимок PostgreSQL (`pg_dump` custom с экспортированным snapshot), список миграций и байты готовых вложений. Весь payload защищён AES-256-GCM со случайным nonce; внутри проверяются размеры и SHA-256. Архив не содержит серверные переменные окружения. Доступ к источнику БД выдан отдельной роли только для чтения. Архивы находятся в отдельном private Blob store, токен которого не передаётся веб-приложению.

Настройки runner находятся в закрытом GitHub Environment `orvo-preview-operations`, разрешённом только для `main`:

| Имя | Назначение |
| --- | --- |
| `ORVO_BACKUP_SOURCE_DATABASE_URL` | Прямой URL роли только для чтения |
| `ORVO_BACKUP_SOURCE_BLOB_TOKEN` | Чтение исходных вложений через отдельный от архива store |
| `ORVO_BACKUP_BLOB_TOKEN` | Запись/чтение архивов и retention |
| `ORVO_BACKUP_KEY_B64` | Случайный ключ шифрования 32 байта в base64 |
| `ORVO_RECONCILE_SECRET` | Только восстановление доставки outbox |
| `VERCEL_AUTOMATION_BYPASS_SECRET` | Доступ автоматизации через защиту Preview |
| `ORVO_DEPLOYMENT_URL` (variable) | Точный адрес действующего Preview |

Ключ OpenAI и пароль владельца в GitHub Actions не передаются. Сохраните независимую защищённую копию ключа архива и `BETTER_AUTH_SECRET`: доступ только к Blob без ключа не восстанавливает данные. Исходный Blob SDK token технически позволяет запись, поэтому он остаётся только в доверенном runner; отдельного read-only SDK token здесь нет.

Ручной запуск с переменными окружения runner:

```sh
node --import tsx scripts/backup.ts --output /private/orvo.orvobak --upload --retention-days 14
node --import tsx scripts/restore.ts --archive /private/orvo.orvobak --dry-run
```

Нужны PostgreSQL client tools не старше сервера; для текущего Neon используются `pg_dump`, `pg_restore`, `psql` версии 18. TLS проверяется (`verify-full`), libpq нужен доверенный CA bundle. Пути переопределяются `PG_DUMP_BIN`, `PG_RESTORE_BIN`, `PG_PSQL_BIN`, `PGSSLROOTCERT`.

## Восстановление

1. Создайте отдельную пустую БД и отдельный private Blob store. Не направляйте работающий сайт на них до окончания проверки.
2. Задайте `ORVO_RESTORE_TARGET_DATABASE_URL`, `ORVO_RESTORE_TARGET_BLOB_TOKEN`, новый `ORVO_RESTORE_TARGET_RUNTIME_SECRET` и `ORVO_RESTORE_ACK=EMPTY_ISOLATED_TARGET` в закрытом окружении runner.
3. Проверьте архив через `--dry-run`, затем выполните `--apply`. Можно использовать `--blob-path orvo-backups/<backup-id>.orvobak` вместо локального `--archive`.
4. Скрипт запрещает исходную/живую БД и исходное/архивное файловое хранилище. Проверяет GCM и все SHA-256. Существующие target-файлы допускаются только как точное подмножество этого архива с совпадающими хешами; чужие объекты блокируют операцию.
5. Импорт SQL и карантин выполняются одной транзакцией `psql`. Ошибка оставляет БД пустой; уже созданные точные Blob-объекты допускают безопасный повтор. Скрипт не удаляет чужие файлы и не применяет `--clean`.
6. Все незавершённые задачи ставятся на паузу, старые runtime bindings удаляются, подтверждения отзываются, неопределённые расходы не обнуляются. Сессии и grants удаляются; TOTP сохраняется. Старые архивы могут содержать отменённые recovery credentials: запускайте актуальные миграции и код с запретом резервного входа до открытия доступа.
7. Для нового deployment задайте фактически новый `ORVO_RUNTIME_SECRET` из подготовленного target secret, совместимый auth secret и новые подключения. Проверяйте модель заново. Возобновляйте задачи вручную после сверки неизвестных внешних расходов.

## Ограничения и контроль

- GitHub расписания работают с default branch, могут задерживаться и не являются SLA. Публичный репозиторий с длительной неактивностью может получить отключённые расписания. Проверяйте свежесть последнего успешного запуска и копии; внешнее оповещение о просроченной копии пока не подключено.
- Пятиминутный reconciler является резервом, обычная доставка идёт через Vercel Queue. Редкие неопределённые исходы требуют ручной сверки.
- Скрипт рассчитан максимум на 500 готовых вложений по 10 MiB. Нужны место на runner и квота хранилища; увеличение объёма требует проверки лимитов.
- Native restore history Neon не заменяет отдельные копии файлов и зашифрованный архив.
- Production получает отдельные БД, файловое хранилище и серверные секреты. Перенос ключа модели в Production и публичное продвижение не выполняются автоматически.

Первичные ограничения платформ: [Vercel Queues](https://vercel.com/docs/queues), [GitHub scheduled workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [Neon history window](https://neon.com/docs/postgres/backup-restore/history-window).
