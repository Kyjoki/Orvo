# Запуск, размещение и восстановление

## Окружение

Используйте Node.js 24+ и зафиксированные `package-lock.json` зависимости через `npm ci`. Точная версия eve указана в `package.json`; инструкции ниже опираются на поставленные вместе с ним руководства:

- `node_modules/eve/docs/guides/frontend/nextjs.mdx`;
- `node_modules/eve/docs/guides/deployment/self-hosting.md`;
- `node_modules/eve/docs/guides/deployment/vercel.mdx`.

После обновления eve перечитайте их: topology и Workflow protocol могут измениться. Облачное размещение Orvo в этой работе не выполнялось.

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Рабочая PostgreSQL, включая требуемые хостом TLS-настройки |
| `BETTER_AUTH_URL` | Канонический origin приложения; HTTPS при размещении |
| `BETTER_AUTH_SECRET` | Случайный секрет сессий, минимум 32 символа |
| `ORVO_RUNTIME_SECRET` | Отдельный случайный служебный секрет, минимум 32 символа |
| `ORVO_RUNTIME_URL` | Origin Next API, доступный процессу eve; для локальной интеграции также входная точка транспорта runtime |
| `OPENAI_API_KEY` | Серверный ключ OpenAI для провайдера OpenAI API; ключ не отправляется в Gateway |
| `AI_GATEWAY_API_KEY` | Серверный ключ Vercel AI Gateway при выборе провайдера Gateway |
| `S3_ENDPOINT` | Необязательный endpoint совместимого хранилища |
| `S3_REGION` | Регион S3 |
| `S3_BUCKET` | Приватный bucket вложений |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Ограниченные серверные credentials bucket |
| `ORVO_OWNER_EMAIL`, `ORVO_OWNER_NAME`, `ORVO_OWNER_PASSWORD` | Только однократный процесс создания владельца; пароль минимум 12 символов |
| `ORVO_TEST_MODE` | `1` только для локальных изолированных проверок; в рабочем режиме отключён |
| `ORVO_TEST_DB_NAME`, `ORVO_TEST_DB_DIR` | Необязательный выбор локальной тестовой БД внутри `.orvo/test-db/` |
| `ORVO_WORKSPACE_ID` | Необязательный идентификатор пространства; полезен для изоляции тестов |
| `EVE_NEXT_PRODUCTION_PORT` | Необязательный loopback-порт встроенного eve при локальном production запуске |
| `EVE_NEXT_PRODUCTION_ORIGIN` | Только для отдельно управляемого eve-хоста; отключает автоматический запуск eve интеграцией |
| `EVE_PUBLIC_ROUTE_PREFIX` | Только если runtime размещается под дополнительным префиксом; одинаково при сборке и запуске |

Значения секретов не включайте в Git, инструкции, снимки экрана и логи. `.env.local`, `.orvo/`, `.eve/` и `.output/` игнорируются Git. В production используйте secret manager/окружение хоста; скрипты `db:migrate` и `owner:create` сейчас читают `.env.local`, поэтому запускайте их в доверенном административном окружении с приватным файлом либо эквивалентно через Node с переменными процесса.

## Первичная настройка

1. Создайте PostgreSQL и закрытый S3 bucket; подготовьте минимальные права приложения на объекты его bucket. Включите TLS и политику резервирования у поставщиков.
2. Задайте серверное окружение. `ORVO_TEST_MODE=1` запрещён для рабочего размещения; PGlite не является облачной БД.
3. Выполните `npm ci` и `npm run db:migrate` одним административным процессом до приёма трафика.
4. Создайте одного владельца через `npm run owner:create`. Передавайте пароль скрытым вводом/secret manager; пример PowerShell есть в README. Удалите bootstrap-пароль из рабочего окружения после создания.
5. Запустите сервер, войдите, выберите модель, выполните проверку подключения и создайте собственных агентов с нужными именами, обязанностями и инструкциями. Роли команды разработки не добавляются в офис автоматически.

## Локальная production сборка / собственный Node-хост

Для topology `withEve` официальное руководство требует отдельно собрать eve до `next start`:

```powershell
npm run build
npm start
```

`npm run build` последовательно выполняет `eve build` и `next build`. Сборка
только `next build` не обновляет `.output` агента: `next start` может запустить
устаревшую серверную логику при новом интерфейсе. После изменения authored
workflow/tool кода собирайте обе части перед перезапуском.

Для локальной проверки production-сборки сохраняйте одинаковую сборку и
окружение при всех последующих запусках:

```powershell
$env:WORKFLOW_LOCAL_QUEUE_CONCURRENCY = '1'
npm run build
npm start
```

В установленном eve 0.80.1 встроенная интеграция явно передаёт Local World
`dataDir = <рабочий каталог>/.eve/.workflow-data`. Это переопределяет официальный
`WORKFLOW_LOCAL_DATA_DIR`: одной этой переменной нельзя разделить development и
production в одном checkout. Такое поведение проверено в поставленном
`dist/src/internal/application/compiled-artifacts.js`. Для изоляции используйте
отдельные checkout с отдельными постоянными томами; совместный каталог не
подтверждает совместимость development-сессий с production-сборкой.

Интеграция
`withEve` запускает `eve dev` без `--resume`; автоматическое восстановление после
полного перезапуска development-сервера здесь не подтверждается. Для проверки
сохранённого ожидания используйте ту же production-сборку и тот же каталог
данных до и после перезапуска. [Параметры Local World](https://workflow-sdk.dev/worlds/local)
включают восстановление активных запусков и ограничение конкуренции очереди.

В Windows при development hot reload наблюдалась ошибка файловой операции
`EPERM rename` Local World. Исходные состояния сохранены; исправление SDK не
имитируется приложением. Статус проверок отдельной стабильной production-сборки
фиксируется в `docs/progress.md`. Local World предназначен для локальной
разработки и единственного экземпляра; рабочее размещение требует подходящего
Vercel/Postgres World и отдельной проверки восстановления.

Текущий `start` привязан к `127.0.0.1`: ставьте перед ним TLS reverse proxy на том же хосте. Процесс-менеджер должен перезапускать сервис. `withEve` запускает собранный `.output/server/index.mjs` на стабильном loopback-порту и проксирует runtime. При отдельном управлении eve-процессом настройте `EVE_NEXT_PRODUCTION_ORIGIN` и private route prefix согласно установленному руководству; простой запуск `next start` без eve build не достаточен.

Локальный Workflow world хранит данные в `.eve/.workflow-data`. Закрепите этот каталог за постоянным томом, сохраняемым при замене контейнера. Не очищайте весь `.eve/` как обычный build cache, если внутри находится runtime state. Локальный world не следует считать проверенным общим хранилищем для нескольких независимых реплик. Несколько реплик требуют совместимого Workflow world и отдельной проверки конкуренции/восстановления.

Прокси должен пропускать `/eve/` и `/.well-known/workflow/` без поломки callback-маршрутов. Защита пользовательского входа не должна подменять служебную авторизацию runtime. `ORVO_RUNTIME_URL` должен быть доступен из фактического процесса/сервиса eve, включая обратные RPC к Next API. Локальный `127.0.0.1` в разных контейнерах обозначает разные сетевые пространства.

## Vercel

Orvo использует Next.js-centered `withEve`; установленная интеграция создаёт отдельный eve service и Workflow routes в том же проекте. Для этой topology используйте сборку Next.js, а не второй независимый движок исполнения. При подготовке размещения проверьте актуальный output интеграции, соединение eve → Next RPC, защищённые callback endpoints и внешнюю PostgreSQL. Диск функции и `.orvo/` не являются постоянным хранилищем.

Проверку модели текущий код выполняет с `AI_GATEWAY_API_KEY`, поэтому одного платформенного OIDC недостаточно для этого пути без адаптации. Крупные вложения идут прямо в S3 по краткоживущему URL, а не через обычное JSON тело функции. Настройте CORS bucket для разрешённого origin, PUT и нужного Content-Type; запретите публичное чтение. Выдача URL, чтение и валидация после загрузки реализованы в коде, живой bucket не проверялся.

Создание проекта, платных ресурсов и публикация выполняются отдельным явно разрешённым действием. Здесь нет подтверждения готового production deployment, гарантий времени фонового запуска или испытанного восстановления на Vercel.

## Диагностика

`/api/health` подтверждает ответ Next HTTP, но не readiness зависимостей. Для приёмки конкретного размещения проверьте отдельно:

1. Вход владельца; unauthenticated запросы не дают данные пространства.
2. Проверку реальной сохранённой модели и ограниченное тестовое задание; это платные операции при настоящем провайдере.
3. Сохранение `workflowRunId`, этапа, Markdown, токенов и уведомления.
4. Перезагрузку вкладки и перезапуск сервиса во время ожидания подтверждения; продолжение ровно той операции после входа.
5. Прямую загрузку и закрытое скачивание TXT/Markdown/PDF из реального bucket.
6. Параллельное подтверждение с двух клиентов, отмену и лимит.

`/eve/v1/health` — endpoint runtime, но сам по себе не доказывает прохождение задания или доступность модели. Не выводите bearer-секреты в командной строке, CI logs и диагностических снимках.

Pending outbox доставляется на запросах к `/api/state` и `/api/command`, а также
служебным запросом из Next instrumentation каждые 10 секунд на постоянно
работающем Node-хосте. Служебный endpoint требует bearer-секрет. Принятые eve
задания не зависят от открытой вкладки; instrumentation повторяет только
доставку сохранённых команд и запусков, а не исполняет модельные этапы.
Этот интервал не является гарантированным планировщиком в serverless-среде.
Для такого размещения нужен надёжный внешний механизм пробуждения outbox и
проверка восстановления; сам факт наличия interval этого не подтверждает.

## Резервные копии

Сохраняйте вместе логическую БД и связанные файлы. SQL содержит текстовые артефакты и метаданные вложений; bucket содержит их исходные байты. Runtime state нужен для продолжения незавершённых запусков.

1. Включите автоматические PostgreSQL backups/PITR у поставщика. Для ручного согласованного снимка временно остановите приём новых задач и изменения данных, дождитесь безопасной границы выполнения.
2. Снимите PostgreSQL через `pg_dump` в custom format и сохраните зашифрованную копию вне сервера. Передавайте credentials через штатный защищённый механизм клиента; не вписывайте пароль в shell-команду.
3. Сохраните приватные объекты S3 с ключами и версиями; настройте versioning/lifecycle и отдельную резервную копию. Объектное versioning само по себе не защищает от потери аккаунта.
4. Для self-hosting при остановленном runtime сделайте согласованный snapshot постоянного `.eve/.workflow-data` вместе с БД. Для управляемого Workflow используйте возможности сохранения/восстановления поставщика; файловая копия serverless диска не заменяет их.
5. Запишите commit, версию схемы, eve/Workflow и расположение snapshots. Секреты храните/восстанавливайте отдельно в secret manager, с ограниченным доступом.

## Восстановление

1. Поднимите изолированное окружение с тем же commit и версиями зависимостей, восстановите секреты, PostgreSQL и bucket. Не направляйте на него пользовательский трафик до проверки.
2. Восстановите compatible runtime state и маршруты. Не запускать два экземпляра одного локального world; не отправлять задачу повторно без проверки её `task_runs`, шагов и резервов.
3. Выполните необходимые миграции одним процессом. Проверьте владельца, сохранённые профили ваших агентов, память, скачивание артефактов и вложений.
4. Проверьте отдельную задачу в ожидании, одноразовое решение, продолжение и отмену. Вызов с неизвестным исходом не повторяйте вслепую: сохраните резерв и проверьте провайдера.
5. Переключите трафик после проверок; зафиксируйте измеренное время восстановления и потерю данных. Такие измерения ещё не выполнены, RPO/RTO не обещаны.

Локальная PGlite подходит для демонстрации и тестов. Её файловую копию делайте только после остановки единственного процесса-владельца; это не инструкция production резервирования PostgreSQL.

Во время разработки прежний тестовый каталог `app` оказался повреждён после принудительного `process.exit` CLI до завершения записи БД. Он сохранён для диагностики, не перезаписан. Текущее игнорируемое `.env.local` указывает на новый локальный `app-verified`. Миграции и создание владельца теперь явно ожидают закрытия БД; PGlite изолирована в `scripts/embedded-db.mjs` с IPC. Не копируйте локальные тестовые данные в рабочую PostgreSQL и не считайте замену тестового каталога проверкой аварийного восстановления production.

## CI и зависимости

`.github/workflows/ci.yml` выполняет на Node.js 24 `npm ci`, typecheck, доменные/runtime unit tests и production сборку. Workflow не передаёт ключи модели, не создаёт инфраструктуру и не запускает платную генерацию. Загрузка npm-пакетов требует сети. До фактического запуска на GitHub это только подготовленная конфигурация CI.

На момент последнего локального аудита осталось три moderate предупреждения в транзитивной цепочке eve/just-bash/sprintf. Shell и универсальные исполняемые инструменты Orvo отключены; это не устраняет предупреждения из дерева зависимостей. Перед публикацией повторите аудит зафиксированного lockfile и оцените доступное совместимое обновление.
